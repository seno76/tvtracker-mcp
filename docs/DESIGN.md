> * раздел «Этапы» — план на момент старта; все семь закрыты, фактическое состояние
>   и найденные по дороге ошибки описаны в [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md)
>   и [`EVALS.md`](EVALS.md).
>
> Актуальное устройство кода — [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Context

Учебный проект по разделу 4 road map «ИИ-агенты и Claude»: собственный MCP-сервер,
задействующий все три серверных примитива (tools, resources, prompts) и дающий
строчку в резюме. Источник данных — TVmaze (сериалы, без API-ключа, лицензия CC BY-SA).

Требование, определяющее весь дизайн: **сервер не должен быть обёрткой над API**.
Обёртка транслирует эндпоинты в инструменты один к одному; ценность такого сервера
нулевая, потому что то же самое агент получил бы через generic-инструмент HTTP.

Сервер оправдан только тогда, когда отвечает на вопросы, на которые **ни TVmaze,
ни локальная база поодиночке ответить не могут**. В этом проекте таких вопросов три:

1. «Найди сериал по описанию, я не помню названия» — TVmaze ищет **только по названию**,
   поиска по тексту описания в API нет вообще.
2. «Что у меня накопилось» — пересечение личного прогресса просмотра с датами выхода серий.
3. «Стоит ли продолжать» — рейтинговый профиль по сезонам в сопоставлении с моими оценками.

Всё три считает наш код. Это и есть граница между продуктом и обёрткой.

### Замеры API (проверено 2026-09-07)

| Факт | Значение | Следствие для дизайна |
| --- | --- | --- |
| Индекс сериалов `/shows?page=N` | страницы 0–379, ~240 шт/стр, ~92 000 сериалов | полный корпус выкачивается за 380 запросов (~4 мин) |
| Размер страницы индекса | ~374 КБ | сырой корпус ~140 МБ, после чистки полей ~35 МБ |
| Среднее описание | 208 символов, 25 языков | корпус реально индексируемый; нужен фильтр по языку |
| `/shows/67/episodes` | 467 серий, **416 КБ** | ~100k токенов на один вызов — список эпизодов НИКОГДА не отдаётся целиком |
| Rate limit | ~20 запросов / 10 сек на IP, 429 | backoff обязателен, лимит достижим при первом же обходе |
| Ключ API | не требуется | `git clone && uv run` работает у любого |
| Python / SQLite | 3.11 / 3.39 с FTS5 | полнотекстовый поиск без единой зависимости |

## Принципы (чем проверяется «не обёртка»)

Источник — Anthropic, «Writing effective tools for agents», плюс отраслевые практики MCP.

1. **Инструмент = сценарий, не эндпоинт.** Типовой запрос закрывается за 1–2 вызова.
   Четыре вызова на сценарий = провал дизайна.
2. **Консолидация.** 5 инструментов на весь сервер, изменения состояния — через один
   инструмент с enum-действием. Ориентир отрасли: 1–10 активных инструментов.
3. **Неймспейсинг.** Префиксы `show_`, `episode_`, `tracking_`, `watch_`.
4. **Семантика вместо идентификаторов.** На вход и выход — slug `severance-2022`,
   числовой `id` TVmaze живёт только внутри. Жанры, статусы, номера серий —
   человекочитаемыми строками (`3x04`), не кодами.
5. **Бюджет контекста как параметр дизайна.** По умолчанию 5–7 полей, `response_format`
   переключает на детальный вид, усечение всегда сопровождается подсказкой,
   как сузить запрос.
6. **Ошибки чинят следующий вызов.** Не «404», а что именно не так и что подставить.
7. **Ответ обогащён собственным состоянием.** Каждый сериал в выдаче помечен
   «отслеживаю, 3x04 / смотрел / новый». Этого в TVmaze нет.
8. **Оценка вместо ощущений.** Набор из 12 задач, метрики — число вызовов и токены
   на сценарий. Дизайн меняется по замерам.

## Архитектура

```
MCP layer      server.py — регистрация tools/resources/prompts, ничего больше
   |
Domain         backlog.py, taste.py, verdict.py, format.py — чистая логика,
   |           тестируется без сети и без БД
Index          fts.py (BM25) + vectors.py (опц.) + hybrid.py (RRF-слияние)
   |
Storage        SQLite: корпус, кэш эпизодов, трекинг, индексы
   |
Source         tvmaze/client.py — httpx, backoff, ETag, соблюдение лимита
```

Смысл разделения: домейн-слой не знает ни про MCP, ни про TVmaze. Логику бэклога
можно протестировать на выдуманных данных за миллисекунды, а сервер поменять
на CLI или HTTP-API, не трогая её.

### Структура проекта

```
tvtracker-mcp/
  src/tvtracker/
    server.py            # точка входа, stdio
    tools/               # show_search, show_profile, episode_search,
                         # tracking_update, watch_next
    resources.py
    prompts.py
    domain/              # backlog, taste, verdict, formatting
    index/               # fts, vectors, hybrid
    storage/             # schema.sql, repo.py, sync.py
    tvmaze/              # client.py, models.py
  evals/tasks.yaml       # 12 сценариев + метрики
  tests/
  README.md              # атрибуция TVmaze (CC BY-SA) обязательна
```

Зависимости: официальный Python SDK для MCP + `httpx`. SQLite из stdlib.
Опционально на этапе 5: `fastembed` + `sqlite-vec`.
Точный API SDK сверить в актуальной документации на `modelcontextprotocol.io`
перед стартом — он меняется от ревизии к ревизии.

## Модель данных (SQLite)

```sql
shows(slug PK, tvmaze_id, name, name_local, type, language, genres_json,
      status, premiered, ended, avg_runtime, rating, weight, network,
      summary_clean, updated_at)          -- корпус, ~92k строк

shows_fts                                  -- FTS5 внешнего содержимого:
                                           -- name, name_local, genres, summary_clean

episodes(show_slug, season, number, name, airstamp, runtime, rating,
         summary_clean, kind, PK(show_slug,season,number))
                                           -- ЛЕНИВО: только отслеживаемые сериалы

episodes_fts                               -- FTS5 по name + summary_clean

tracking(show_slug PK, state, season, number, rating, note, started_at, updated_at)
                                           -- state: watching | paused | finished | dropped

sync_state(key, value)                     -- метка последнего /updates/shows
```

Решения, которые здесь зашиты:

- **Корпус сериалов — полный, эпизоды — ленивые.** 92k сериалов с описаниями это ~35 МБ
  и один обход. Эпизоды для всех — это миллионы строк и сотни мегабайт, поэтому
  тянутся и индексируются только при `tracking_update(action="track")`.
  Классический just-in-time retrieval.
- **`summary_clean`** — описание, очищенное от HTML (`<p>…</p>` приходит от API как есть).
  Хранится и индексируется уже чистым.
- **`kind`** эпизода (`regular` / `special` / `insignificant`) — обязателен: без него
  бэклог требует «досмотреть» рождественский спешл, которого нет в сюжетной линии.
- **`airstamp` (UTC), а не `airdate`.** Вопрос «вышло уже или нет» корректно решается
  только по UTC-метке, иначе ошибка в сутки на стриминге и азиатских релизах.
- **slug как ключ.** `severance-2022` = имя + год премьеры, коллизии разрешаются суффиксом.

### Синхронизация

- **Bootstrap**: обход `/shows?page=0..379`, ~380 запросов, соблюдая лимит — около 4 минут.
  Запускается один раз командой `tvtracker sync --full`, не из MCP-инструмента.
- **Инкремент**: `/updates/shows` отдаёт метки времени изменений; обновляем только то,
  что изменилось с прошлого раза. Дешёво, можно раз в сутки.
- **Эпизоды**: `/shows/:id?embed[]=episodes` — один запрос вместо двух;
  обновление для идущих сериалов по `_links.nextepisode`.

## Инструменты (5)

Общие правила: все принимают `response_format: "concise" | "detailed"` (по умолчанию
`concise`); все возвращают текст, а не сырой JSON API; во всех выдачах каждый сериал
помечен статусом отслеживания.

### 1. `show_search`

```
show_search(query, by="auto"|"title"|"description", genre?, status?,
            language?, year_from?, year_to?, min_rating?, limit=8)
```

Один инструмент вместо трёх (поиск по названию, поиск по описанию, фильтрация каталога).
`by="auto"` — если запрос похож на название, работает точный поиск; если это фраза-описание
(«сериал про офис, где сотрудникам разделяют память»), включается поиск по корпусу.

Поиск по описанию — **главная функция сервера**, в TVmaze её нет. Реализация:
FTS5/BM25 по `summary_clean` + `name` + жанрам, на этапе 5 — гибрид с эмбеддингами.

Ответ (concise), одна строка на результат:

```
Severance (2022–, Apple TV, идёт) · драма/фантастика/детектив · 49 мин · 7.6
Сотрудникам корпорации хирургически разделяют память между работой и личной жизнью.
→ отслеживаю, остановился на 2x03

Показаны 8 из 34. Сузить: genre="Sci-Fi" или year_from=2020.
```

Полей 6, а не 40. Ни `image`, ни `_links`, ни `externals` модель не видит никогда.

### 2. `show_profile`

```
show_profile(show, include=["seasons","cast","next"], response_format)
```

Агрегат из четырёх эндпоинтов TVmaze (`/shows`, `/seasons`, `/cast`,
`_links.nextepisode`) плюс два вычисляемых блока, которых в API нет:

- **рейтинговый профиль по сезонам** — средняя оценка серий каждого сезона,
  отсюда видно, где сериал раскачивается и где проседает;
- **позиция пользователя** — где остановился, сколько серий и часов до конца сезона.

Отвечает на «расскажи про сериал» одним вызовом. Обёртка потратила бы четыре.

### 3. `episode_search`

```
episode_search(query, show?, season?, include_specials=false, limit=5)
```

Поиск серии **по описанию**: «серия, где они застряли в лифте». Работает по
`episodes_fts`, то есть по отслеживаемым сериалам (для них эпизоды уже загружены).
Если `show` указан, а эпизодов в кэше нет — подгружает и индексирует на лету.

Защита от спойлеров: по умолчанию не показывает описания серий **после** текущей
позиции пользователя, только факт наличия. Отключается `include_unwatched=true`.
Такого поведения не может быть у обёртки в принципе — оно требует знания прогресса.

### 4. `tracking_update`

```
tracking_update(show, action="track"|"untrack"|"progress"|"rate"|"pause"|"finish",
                episode?, rating?, note?)
```

Консолидация всех изменений состояния в один инструмент с enum вместо шести
отдельных. `episode` принимает человеческий формат `"2x03"`. При `action="track"`
запускается фоновая загрузка и индексация эпизодов сериала.

Ответ подтверждает изменение и сразу даёт следующий шаг:
`Отмечено: Severance 2x03. Дальше — 2x04 «Woe's Hollow», 71 мин, вышла.`

### 5. `watch_next`

```
watch_next(minutes?, mood?, include_new=false, limit=3)
```

Не поиск, а решение: берёт бэклог, фильтрует по свободному времени (по `runtime`
серии, с оглядкой на `averageRuntime`, когда `runtime` пуст), ранжирует по свежести
выхода, длине долга и твоим оценкам сериала. Возвращает 2–3 варианта с одной
строкой обоснования.

Это тот вызов, ради которого затевается сервер: вопрос «что включить» решается
**одним** обращением к инструменту, без предварительных поисков.

## Ресурсы (5)

Ресурс — данные, которые подаёт **приложение или пользователь**, а не модель. Критерий
включения в этот список один: содержимое нужно в контексте **до** того, как модель начала
рассуждать. Всё, что «может понадобиться, а может нет», — инструмент.

Общие решения по всем ресурсам:

- **`mimeType: text/plain`, а не `application/json`.** JSON тратит на скобки, кавычки
  и повторяющиеся имена полей в полтора-два раза больше токенов при той же информации,
  а модель читает плотный текст не хуже. JSON оправдан, когда ответ парсит код;
  здесь его читает только модель.
- **Все ресурсы вычисляются на лету** из локальной БД, без обращения к TVmaze. Значит
  `resources/read` отвечает за миллисекунды и работает, даже когда API лежит.
- **Бюджет.** Суммарно все пять — ориентировочно **~1100 токенов**. Это цена, которую
  ты платишь в каждом запросе, где хост их подставил. Если бюджет вырастет вдвое —
  это повод резать содержимое, а не оправдывать.
- **Нотификация об изменении.** После `tracking_update` сервер шлёт уведомление
  об изменении ресурсов; хост перечитывает их сам, без лишнего инструмента.

Шаблонных ресурсов (URI с подстановкой вида `show://{slug}`) в дизайне сознательно нет:
данные по конкретному сериалу нужны не всегда, а по запросу — это работа `show_profile`.

### 1. `tracking://watching`

| | |
| --- | --- |
| **Название для хоста** | Что я смотрю сейчас |
| **Описание** | Сериалы в активном просмотре с текущей позицией и датой последнего просмотра |
| **mimeType** | `text/plain` |
| **Источник** | таблица `tracking` (`state = watching`) + `episodes` для названий |
| **Объём** | ~10–20 строк, ~200 токенов |
| **Обновляется** | после любого `tracking_update` |

Содержимое:

```
Смотрю сейчас (4):
Severance — 2x03 «Who Is Alive?», последний просмотр 2026-09-02, моя оценка сериала 9
The Bear — 3x08, последний просмотр 2026-08-14
Shogun — 1x10 (финал сезона), последний просмотр 2026-07-30
Slow Horses — 4x02, последний просмотр 2026-06-11

На паузе (2): Foundation (2x04), True Detective (4x03)
```

**Почему ресурс.** Это профиль пользователя в этом домене. Любой вопрос про сериалы —
«что посмотреть», «стоит ли начинать X», «что там с Y» — требует его. Оформив это
инструментом, ты обязываешь модель догадаться, что надо сходить за историей, и тратишь
раунд на то, что известно заранее.

### 2. `tracking://backlog`

| | |
| --- | --- |
| **Название для хоста** | Накопившиеся серии |
| **Описание** | Вышедшие, но не просмотренные эпизоды по отслеживаемым сериалам |
| **mimeType** | `text/plain` |
| **Источник** | `tracking` × `episodes`, фильтр `airstamp <= now()` и `kind = regular` |
| **Объём** | ~10 строк, ~300 токенов |
| **Обновляется** | после `tracking_update` и после синхронизации эпизодов |

Содержимое:

```
Накопилось (по свежести выхода):
Severance          7 серий  ~5ч 45м   свежая вышла 3 дня назад     2x04 … 2x10
Slow Horses        4 серии  ~3ч 00м   свежая вышла 11 дней назад   4x03 … 4x06
The Bear           2 серии  ~1ч 10м   свежая вышла 2 недели назад  3x09, 3x10
Shogun             0 серий            сезон досмотрен, продления нет

Итого: 13 серий, ~9ч 55м. Спецвыпуски не учитываются.
```

**Почему это сердце проекта.** Такого ответа нет ни в TVmaze, ни в твоей базе. Он
рождается на их пересечении: позиция из локального трекинга минус вышедшие серии
по `airstamp` из кэша, с отброшенными `special` и `insignificant`, с суммированием
`runtime` (а где он `null` — по `averageRuntime` сериала). Один этот ресурс отделяет
продукт от обёртки нагляднее всех остальных доводов.

**Граничные случаи, которые обязаны быть в юнит-тестах:** сериал закончился и долгов
больше не будет; серия вышла сегодня, но по UTC ещё не наступила; `runtime = null`;
дейли-шоу с нумерацией по годам (`season: 2026, number: 178`); пропущенный сезон.

### 3. `tracking://schedule`

| | |
| --- | --- |
| **Название для хоста** | Календарь моих сериалов |
| **Описание** | Что из отслеживаемого выходит в ближайшие 14 дней |
| **mimeType** | `text/plain` |
| **Источник** | `episodes` с `airstamp` в будущем + `_links.nextepisode` для идущих |
| **Объём** | ~8 строк, ~200 токенов |
| **Обновляется** | по времени (содержимое меняется само, без действий пользователя) |

Содержимое:

```
Ближайшие 14 дней (сегодня 2026-09-07):
пт 12.09  Slow Horses 4x07 «Cold Water»       Apple TV
вс 14.09  The Morning Show 4x03               Apple TV
ср 17.09  Severance — данных нет, сериал ждёт продления

Дальше горизонта: ничего из отслеживаемого.
```

**Почему ресурс.** Единственный из пяти, который меняется **сам по себе**, без твоих
действий. Модель не может знать, что стоит его перепроверить, — значит подавать его
должен хост.

### 4. `tracking://taste`

| | |
| --- | --- |
| **Название для хоста** | Профиль вкуса |
| **Описание** | Агрегат по истории: жанры со средней оценкой, доля брошенного, предпочитаемая длина |
| **mimeType** | `text/plain` |
| **Источник** | `tracking` со всеми состояниями + жанры и метаданные из `shows` |
| **Объём** | ~15 строк, ~250 токенов |
| **Обновляется** | после `tracking_update` с `action="rate"` / `"finish"` / `"untrack"` |

Содержимое:

```
Профиль вкуса (по 34 сериалам, из них 21 с оценкой):
Люблю:      детектив 8.6 (5) · фантастика 8.4 (7) · драма 8.0 (9)
Прохладно:  комедия 6.2 (4) · реалити 5.0 (1)
Досматриваю: 62% начатого. Брошено чаще всего на 1-2 сезоне.
Длина:      предпочитаю 45–60 мин; сериалы длиннее 20 серий в сезоне почти всегда бросаю.
Площадки:   Apple TV (7), HBO (5), Netflix (5)
Языки:      English (31), Korean (2), Danish (1)

Последние оценки: Shogun 9, Severance 9, The Bear 7, True Detective 5 (брошен)
```

**Почему ресурс.** Это основание любой рекомендации. Если добывать его инструментом,
модель будет то запрашивать его, то не запрашивать — и качество советов станет
случайным от разговора к разговору. Ресурс делает поведение воспроизводимым.

**Честная оговорка в описании ресурса:** цифры считаются по малой выборке. Формулировка
должна это отражать («по 21 оценке»), иначе модель начнёт выдавать статистику
из четырёх сериалов за устойчивый вкус.

---

### 5. `catalog://facets`

| | |
| --- | --- |
| **Название для хоста** | Допустимые значения фильтров |
| **Описание** | Жанры, типы, статусы и языки, реально встречающиеся в локальном корпусе |
| **mimeType** | `text/plain` |
| **Источник** | `SELECT DISTINCT` по корпусу `shows`, пересчитывается при синхронизации |
| **Объём** | ~10 строк, ~150 токенов |
| **Обновляется** | после `sync` (раз в сутки и реже) |

Содержимое:

```
Значения для фильтров show_search:
genre:    Action, Adventure, Anime, Comedy, Crime, Drama, Espionage, Family, Fantasy,
          History, Horror, Legal, Medical, Music, Mystery, Romance, Science-Fiction,
          Sports, Supernatural, Thriller, War, Western
status:   Running | Ended | To Be Determined | In Development
type:     Scripted | Animation | Documentary | Reality | Talk Show | Game Show | News
language: English (61k), Japanese (5.2k), Korean (3.1k), Spanish (2.8k), … всего 25

Жанры чувствительны к написанию: "Science-Fiction", не "Sci-Fi" и не "sci fi".
```

**Почему ресурс.** Точный аналог справочника жанров у киношных API. Без него модель
угадывает написание (`Sci-Fi` вместо `Science-Fiction`), получает пустую выдачу
и делает ложный вывод «в каталоге ничего нет». Последняя строка про написание — не
украшение, а прямая профилактика самой частой ошибки.

**Почему не инструмент.** Справочник нужен при каждом поиске с фильтром и меняется
раз в месяц. Инструмент здесь означал бы лишний раунд перед каждым поиском —
или, что хуже, пропущенный вызов и угаданное значение.

---

## Промпты (4)

Промпт — заготовленная **человеком** форма разговора, запускается явной командой
(в Claude Code — как слэш-команда). Отличие от инструмента: инструмент решает подзадачу
внутри рассуждения модели, промпт задаёт рассуждению рамку целиком.

Общее правило дизайна: **промпты втягивают контекст из ресурсов, а не добывают его
инструментами.** Если шаблон начинается с «сначала вызови такой-то инструмент, чтобы
узнать историю» — примитивы разложены неверно.

---

### 1. `whats_next` — «что включить сейчас»

| | |
| --- | --- |
| **Аргументы** | `minutes` (обязательный, целое), `mood` (опциональный: строка свободной формы) |
| **Втягивает** | `tracking://backlog`, `tracking://watching`, `tracking://taste` |
| **Инструменты** | `watch_next` — не более одного вызова |
| **Ответ** | 2–3 варианта, по одной строке обоснования на каждый |

Рамка шаблона:

```
У пользователя свободно {minutes} минут. Настроение: {mood|не указано}.

Ниже — накопившиеся серии и профиль вкуса.

Правила:
- предлагай ТОЛЬКО то, что уже вышло и лежит в бэклоге;
- серия должна укладываться в {minutes} с запасом 10%;
- не более трёх вариантов, каждый — одна строка обоснования;
- если ничего не подходит по времени, скажи об этом прямо и предложи
  единственную альтернативу, а не список;
- никаких описаний непросмотренных серий: только название и длительность.
```

Последнее правило — та же защита от спойлеров, что и в `episode_search`. Без него
промпт с удовольствием перескажет сюжет серии, которую ты собрался смотреть.

**Критерий приёмки (eval №2):** ответ формируется **без единого вызова инструмента**
ради получения истории — она пришла ресурсами. Допустим максимум один вызов
`watch_next` для ранжирования.

---

### 2. `catch_up` — «что я пропустил»

| | |
| --- | --- |
| **Аргументы** | `since` (опциональный: `"2 недели"`, `"с 1 августа"`; по умолчанию — с последнего просмотра) |
| **Втягивает** | `tracking://backlog`, `tracking://schedule`, `tracking://watching` |
| **Инструменты** | обычно ноль |
| **Ответ** | сводка «вышло / впереди / с чего продолжать» |

Рамка шаблона:

```
Пользователь не следил за сериалами {since}. Составь сводку из трёх частей:

1. Что вышло за это время — по сериалам, с числом серий и общим временем.
2. Что выходит в ближайшие две недели.
3. С чего продолжать: ровно один конкретный совет — сериал и номер серии.

Раздел 3 обязателен и не должен быть списком. Если продолжать нечего —
скажи это прямо, не придумывай занятие.
```

Требование «ровно один совет» — намеренное. Список из шести вариантов возвращает
пользователя ровно в ту растерянность, из-за которой он и спросил.

---

### 3. `find_by_vibe` — «найди по описанию»

| | |
| --- | --- |
| **Аргументы** | `description` (обязательный: свободное описание сюжета или атмосферы) |
| **Втягивает** | `catalog://facets`, `tracking://taste` |
| **Инструменты** | `show_search(by="description")`, при необходимости повторно с фильтрами |
| **Ответ** | 3–5 кандидатов либо один уточняющий вопрос |

Рамка шаблона:

```
Пользователь описывает сериал, названия которого не помнит: «{description}»

Порядок:
1. Вызови show_search с by="description".
2. Если в выдаче есть явный лидер — назови его и спроси, он ли это.
3. Если кандидатов много и они разнородные — задай ОДИН уточняющий вопрос
   (страна, десятилетие, тон, длина) и повтори поиск с фильтром.
   Значения фильтров бери из справочника, не выдумывай.
4. Если ничего не найдено — предложи переформулировать описание другими словами,
   объяснив, что поиск идёт по тексту описаний.

Помечай сериалы, которые пользователь уже смотрел или бросал.
```

Это единственный промпт, который **проектирует диалог, а не ответ**: поиск по описанию
почти никогда не попадает с первого раза, и воронка «широкий запрос → один вопрос →
сужение» работает лучше, чем выдача двадцати кандидатов сразу. Шаг 4 честно объясняет
пользователю природу поиска — лексический индекс не понимает пересказ смысла, ему
нужны слова, близкие к тексту описания.

---

### 4. `season_verdict` — «стоит ли продолжать»

| | |
| --- | --- |
| **Аргументы** | `show` (обязательный: название или slug) |
| **Втягивает** | `tracking://watching`, `tracking://taste` |
| **Инструменты** | `show_profile` — ровно один вызов |
| **Ответ** | вердикт из трёх вариантов с обоснованием на 2–3 строки |

Рамка шаблона:

```
Пользователь на {позиция из ресурса} сериала «{show}» и сомневается, продолжать ли.

Возьми профиль сериала (рейтинги по сезонам) и сопоставь с профилем вкуса.
Дай ОДИН вердикт: «продолжай», «перетерпи до N-й серии», «бросай».

Обоснование — 2–3 строки, обязательно с числами: как менялся рейтинг по сезонам
и как жанр соотносится с тем, что пользователь обычно оценивает высоко.

«Бросай» — допустимый и часто верный ответ. Не подслащивай:
доля брошенного в профиле показывает, что пользователь и сам так делает.
Не пересказывай сюжет непросмотренных серий.
```

**Зачем этот промпт нужен.** Он выжимает пользу из данных, которые в API лежат мёртвым
грузом: у каждой серии есть `rating.average`, а значит виден профиль качества по сезонам —
где сериал раскачивается, где проседает, где его стоит бросить. Ни один клиент TVmaze
этого не показывает, и сама формулировка «перетерпи до 3x05» невозможна без агрегации
на нашей стороне.

---

## Политика бюджета контекста

1. Список эпизодов целиком не отдаётся никогда — только окно вокруг позиции
   (предыдущая, текущая, следующие три).
2. Из каждого объекта API выбрасываются `image`, `_links`, `url`, `externals`,
   `dvdCountry`, `webChannel.officialSite` — в контекст они не попадают ни при каких флагах.
3. `summary` чистится от HTML и режется до ~200 символов в concise-режиме.
4. Любое усечение сопровождается строкой «показано N из M» и конкретной подсказкой,
   каким параметром сузить.
5. Целевой размер ответа concise-инструмента — до ~600 токенов.

## Отказы и лимиты

- **429 от TVmaze**: экспоненциальный backoff с jitter, максимум 3 попытки; при
  исчерпании модели уходит `Источник временно ограничил доступ, повтори через ~10 секунд;
  локальный поиск и трекинг работают.` — то есть указание на то, что ещё доступно.
- **Сериал не найден**: не пустой список, а `По запросу «X» ничего. Ближайшие по названию:
  A, B. Или опиши сюжет — я умею искать по описанию (by="description").`
- **Неверный формат эпизода**: `Ожидаю "2x03" или season=2, number=3. Получено "S02E03".`
- **Эпизоды ещё индексируются**: честный ответ о том, что данные подгружаются,
  с оценкой времени — вместо пустой выдачи, на которую модель ответит выдумкой.
- Бесконечный ретрай исключается явным потолком попыток на уровне клиента.

---

## Безопасность

1. **Непрямая инъекция.** `summary` сериалов и серий пишут пользователи TVmaze и
   через выдачу он попадает прямо в контекст. Меры: очистка HTML, жёсткое усечение,
   обрамление пользовательского текста явным маркером источника в ответе инструмента.
   Полностью проблема не решается — это ограничение, которое надо знать и записать в README.
2. **Никаких секретов** — ключа у API нет, но `.env` и `.gitignore` заводятся сразу,
   БД в репозиторий не коммитится.
3. **SQL** — только параметризованные запросы; строка пользователя не склеивается
   с FTS-запросом без экранирования спецсинтаксиса FTS5.
4. **Путь к БД** — из конфига, без интерполяции пользовательского ввода.
5. **Аннотации инструментов**: `show_search`, `show_profile`, `episode_search`, `watch_next`
   помечаются как read-only, `tracking_update` — как изменяющий данные. Точный
   формат аннотаций сверить по актуальной ревизии спецификации MCP.

## Оценка качества (evals)

Без замеров «лучшие практики» остаются словами. `evals/tasks.yaml` — 12 сценариев:

1. «Сериал, где сотрудникам разделяют память» → Severance в топ-3.
2. «Что посмотреть, свободен час» → ответ **без единого вызова** для получения истории.
3. «Что вышло, пока меня не было две недели».
4. «Отметь, что досмотрел второй сезон Severance».
5. «Серия, где они застряли в лифте» (в рамках отслеживаемого сериала).
6. «Стоит ли продолжать смотреть X после третьего сезона».
7. «Найди что-то похожее на то, что я оцениваю выше восьми».
8. «Комедии до 30 минут, которые уже закончились».
9. Несуществующий сериал — проверка, что ошибка ведёт к верной второй попытке.
10. Запрос во время 429 — проверка деградации.
11. Спойлерный запрос по непросмотренной серии.
12. Сериал с 400+ сериями — проверка, что контекст не взорвался.

Метрики на каждый сценарий: **число вызовов инструментов**, **токены ответа**,
достигнут ли результат. Дизайн правится по числам.

Целевые пороги: типовой сценарий — 1–2 вызова; ответ concise — до ~600 токенов;
сценарий 12 — не более 2 000 токенов на вызов.

## Этапы

| Этап | Содержание | Критерий готовности |
| --- | --- | --- |
| 1 | Клиент TVmaze с backoff, схема БД, `sync --full` | корпус 92k сериалов лежит в SQLite, ни одного 429 в логе |
| 2 | Скелет MCP-сервера, `show_search` по названию, stdio | в MCP Inspector виден `tools/list`, вызов возвращает компактный текст |
| 3 | FTS5 по описаниям, `by="description"`, `catalog://facets` | сценарий 1 из evals проходит |
| 4 | Трекинг: `tracking_update`, ленивая загрузка эпизодов, ресурсы `watching` / `backlog` / `schedule` | сценарий 2 проходит **без вызова инструментов** для истории |
| 5 | `show_profile`, `episode_search`, `watch_next`, `tracking://taste`, промпты | сценарии 3–8 проходят |
| 6 | Прогон evals, замер токенов и вызовов, правка описаний инструментов | таблица «было/стало» по числу вызовов |

Опционально после 6: гибридный поиск (эмбеддинги `fastembed` + `sqlite-vec`,
слияние с BM25 через RRF) и перевод на Streamable HTTP без изменения доменного слоя —
живая проверка тезиса о разделении слоя данных и транспорта.

## Верификация

1. **MCP Inspector** — до подключения к Claude Code: увидеть сырые `tools/list`,
   `resources/list`, `resources/read`, `tools/call` и убедиться, что примитивы
   объявлены так, как задумано.
2. **Юнит-тесты домейна** — `backlog`, `taste`, `verdict` на фикстурах, без сети:
   граничные случаи (спецвыпуски, сериал закончился, `runtime = null`, дейли-шоу
   с нумерацией по годам).
3. **Тест клиента** — искусственный 429, проверка backoff и потолка попыток.
4. **Прогон evals** — 12 сценариев, таблица метрик.
5. **Неделя реального использования** в Claude Code — единственная проверка,
   которая ловит то, что не ловят тесты: какие вопросы задаются на самом деле.

## Принятые допущения

- Один пользователь, локальный запуск, stdio-транспорт. Мультиарендность, OAuth
  и удалённый транспорт вне объёма — они утроят код и ничего не добавят
  к пониманию примитивов.
- Только TVmaze. Второй источник (TMDB для фильмов) — отдельный проект.
- Векторный поиск вынесен за основной объём: FTS5 закрывает сценарий поиска
  по описанию на приемлемом уровне и не тянет 100+ МБ зависимостей.
