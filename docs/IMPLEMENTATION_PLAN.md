# План реализации `tvtracker-mcp`

Дизайн примитивов зафиксирован в [`DESIGN.md`](DESIGN.md) и здесь не пересматривается.
Этот документ отвечает на другой вопрос: **в каком порядке это писать, чем логировать и
чем доказывать, что очередной этап ничего не сломал.**

Проверенные факты окружения (замерено на этой машине 2026-09-08):

| Факт | Значение |
| --- | --- |
| Python | 3.11.2 |
| SQLite | 3.39.4, FTS5 доступен |
| MCP Python SDK | **2.2.0** — это v2, не v1 |
| Точка входа SDK | `from mcp.server import MCPServer` |
| Транспорт | stdio (по умолчанию), Streamable HTTP — опция после этапа 6 |

> **Важно про SDK.** Дизайн писался под v1 (`FastMCP`). Установлен v2, где класс называется
> `MCPServer`, контекст живёт в `mcp.server.mcpserver.Context`, ошибки инструментов — в
> `mcp.server.mcpserver.exceptions.ToolError`, а протокольная возможность logging
> **объявлена устаревшей** ревизией спецификации 2026-07-28 и не заменена. Отсюда все решения
> по логированию ниже. Источники:
> [SDK docs](https://py.sdk.modelcontextprotocol.io/),
> [What's new in v2](https://py.sdk.modelcontextprotocol.io/whats-new/),
> [Handlers → Logging](https://py.sdk.modelcontextprotocol.io/handlers/logging/),
> [спецификация 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28).

### Ошибки, найденные на настоящих данных

Каждая закреплена тестом в `tests/regression/`. Все семь всплыли только после того, как
код встретился с корпусом или с живым SDK, — юниты на фикстурах их не ловили.

| Что сломалось | Почему |
| --- | --- |
| Поиск по описанию возвращал ноль | слова объединялись подразумеваемым `AND`: совпасть должны были все десять сразу |
| «Показаны 3 из 64714» | при `OR` это частотность служебных слов, а не число подходящих сериалов |
| `catalog://facets` выдавал «Running \| Ended \| Running» | `GROUP BY name` группировал по колонке `shows.name`, то есть по названиям сериалов |
| Фильтрация каталога без запроса не работала | третий сценарий `show_search` не был реализован вовсе |
| `UNIQUE constraint failed: shows.slug` | два одноимённых сериала в одной пачке: в БД на момент проверки нет ни одного |
| Ресурсы падали с `ProgrammingError` | SDK выполняет синхронные обработчики в рабочем потоке, соединение SQLite привязано к своему |
| `mcp dev` не мог импортировать `server.py` | `@dataclass` с отложенными аннотациями в модуле, не зарегистрированном в `sys.modules` |
| Пустой `TVTRACKER_LOG_FILE=` ронял логгер | `Path("")` превращается в `Path(".")`, и обработчик открывал каталог как файл |
| Нелатинские названия схлопывались в `show-2017` | slug отбрасывал всё, кроме ASCII, а в корпусе 25 языков |

## Система логирования

Три решения, вытекающие из транспорта и из спецификации.

**1. Только stderr, никогда `print`.** Сервер запускается хостом как подпроцесс, и его
**stdout — это провод протокола**. Стандартный `logging` пишет в stderr по умолчанию;
мы этого не меняем. `print()` в блочно-буферизованном процессе может слиться на провод
при выходе интерпретатора — поэтому его в коде нет вообще.

**2. Конфигурируем до создания сервера.** `MCPServer` сам зовёт `logging.basicConfig(...)`,
а тот не трогает уже существующие обработчики. Значит `configure_logging()` вызывается
первой строкой `server.py` — и выигрывает наша конфигурация, а не SDK-шная.

**3. Протокольный logging не используем.** Возможность `logging` в MCP объявлена
устаревшей ревизией 2026-07-28 и не заменена. Строить на ней нечего; наблюдаемость —
это stderr и (опционально) OpenTelemetry, который SDK эмитит сам.

### Что уже написано в `log.py`

| Элемент | Зачем |
| --- | --- |
| `configure_logging(level, fmt, log_file)` | идемпотентна; `console` для разработки, `json` для разбора; ротация файла 5 МБ × 3 |
| `ContextFilter` + `contextvars` | `request_id`, `operation`, `tool` попадают в каждую запись сами — в обработчиках нет ни одного `request_id=` |
| `JsonFormatter` | одна строка JSON на запись, все `extra`-поля внутри |
| `bind(**fields)` | добавляет поля контекста на время блока |
| `request_scope(operation, **fields)` | id вызова, `duration_ms`, исход: успех — DEBUG, отказ — WARNING с типом исключения |
| приглушение `httpx`/`httpcore` | иначе транспортный шум топит собственные события |

### Что логируется на каждом слое

| Слой | Событие | Уровень | Поля |
| --- | --- | --- | --- |
| `tvmaze/client` | запрос выполнен | DEBUG | `path`, `status`, `duration_ms`, `attempt` |
| `tvmaze/client` | 429 и уход в backoff | WARNING | `attempt`, `sleep_s`, `retry_after` |
| `tvmaze/client` | попытки исчерпаны | ERROR | `path`, `attempts` |
| `storage/sync` | прогресс обхода | INFO | `page`, `of`, `rows`, `elapsed_s` |
| `index/fts` | поисковый запрос | DEBUG | `mode`, `hits`, `took_ms` |
| `tools/*` | вызов инструмента | DEBUG/WARNING | `request_scope`: `tool`, `request_id`, `duration_ms` |
| `tools/*` | усечение выдачи | INFO | `shown`, `total`, `approx_tokens` |
| `domain/*` | ничего | — | доменный слой чистый: он возвращает значения, а не пишет в лог |

Последняя строка — принципиальная. Логи живут на границах (сеть, БД, MCP), а доменные
функции остаются чистыми: их можно гонять тысячами на фикстурах без всякой настройки.

### Метрика, ради которой всё это

`duration_ms` и `tool` из `request_scope` — это тот самый замер «сколько вызовов стоил
сценарий», по которому дизайн правится на этапе 6. Без структурированного лога эта таблица
собирается вручную.

## Стратегия тестирования

Четыре уровня, четыре маркера pytest — они уже объявлены в `pyproject.toml`.

| Маркер | Что покрывает | Скорость | Сеть/БД |
| --- | --- | --- | --- |
| `unit` | `domain/` (бэклог, вкус, вердикт), `format`, `slug`, парсинг `"2x03"`, `log`, `config` | мс | нет |
| `integration` | `storage/` и `index/` поверх реальной SQLite в `tmp_path`; клиент TVmaze поверх `respx` | десятки мс | локально |
| `contract` | MCP-примитивы через in-memory `Client(mcp, raise_exceptions=True)`: `tools/list`, `resources/read`, `prompts/get` | сотни мс | нет |
| `regression` | закреплённые сценарии из `evals/tasks.yaml` на фиксированном срезе данных | секунды | нет |

**Сети в тестах нет ни на одном уровне.** HTTP-слой мокается через
[`respx`](https://lundberg.github.io/respx/) — включая искусственный 429 для проверки
backoff и потолка попыток.

**Контрактные тесты — по документации SDK.** `Client` подключается к объекту сервера
**в памяти**, без подпроцесса и порта; `raise_exceptions=True` показывает настоящую ошибку
вместо санитизированного `"Internal server error"`
([Testing](https://py.sdk.modelcontextprotocol.io/get-started/testing/)).

```python
@pytest.fixture
async def client() -> AsyncIterator[Client]:
    async with Client(mcp, raise_exceptions=True) as c:
        yield c
```

**Регрессия = золотые файлы.** Каждый сценарий из `evals/tasks.yaml` прогоняется на
зафиксированном срезе (~200 сериалов, один сериал с 400+ сериями) и сравнивается с
эталонным текстом ответа в `tests/fixtures/golden/`. Меняется формат вывода — diff виден
сразу, а не через неделю в чате.

### Фикстуры данных

`tests/fixtures/` — три набора, собираются один раз скриптом и коммитятся:

* `shows_sample.json` — ~200 сериалов, включая закончившийся, дейли-шоу с нумерацией по
  годам и сериал без `runtime`;
* `episodes_severance.json`, `episodes_daily.json` — реальные ответы TVmaze;
* `tracking_seed.sql` — состояние трекинга для сценариев 2–7.

### Обязательные граничные случаи (из дизайна, дословно)

Для `domain/backlog.py`: сериал закончился и долгов больше не будет · серия вышла сегодня,
но по UTC ещё не наступила · `runtime = null` (падаем на `averageRuntime`) · дейли-шоу
(`season: 2026, number: 178`) · пропущенный сезон · спецвыпуски и `insignificant`
не попадают в долг.

Для `tvmaze/client.py`: 429 → backoff с jitter → успех · 429 на всех попытках → сообщение
про деградацию, а не исключение наружу · таймаут · битый JSON.

Для безопасности: строка пользователя в FTS5-запросе экранируется (кавычки и операторы
`AND`/`OR`/`NOT`/`NEAR`/`*`), все SQL-запросы параметризованы, HTML из `summary` вычищен.

### Порог качества

`pytest --cov` с порогом **90 % на `src/tvtracker/domain/`** (там вся ценность) и **75 %
общего**. Ниже — этап не считается закрытым.

## Регрессионный контур: что гоняется после каждой реализации

Один и тот же цикл после **каждой** законченной задачи, а не только в конце этапа:

```bash
uv run ruff check . && uv run ruff format --check .   # стиль
uv run mypy                                            # типы, strict
uv run pytest -m unit -q                               # секунда, гоняется на каждое сохранение
uv run pytest -q --cov                                 # весь набор + покрытие
uv run pytest -m regression -q                         # золотые файлы предыдущих этапов
```

Правило: **набор регрессии только растёт**. Каждый закрытый сценарий из `evals/tasks.yaml`
превращается в `regression`-тест и остаётся в наборе навсегда. Если этап 5 меняет формат
ответа `show_search`, золотой файл этапа 3 обязан быть обновлён осознанно — отдельным
коммитом с объяснением, почему новый вывод лучше.

Позже — `pre-commit` с `ruff` + `mypy` и GitHub Actions на матрице 3.11/3.12, гоняющие
ровно эти пять команд.

## Этапы реализации

Каждый этап: что пишем → чем логируем → чем тестируем → критерий готовности.
Критерий формулируется так, чтобы его нельзя было «почти» выполнить.

### Этап 1 — источник и хранилище

**Пишем.** `tvmaze/client.py` (`httpx.AsyncClient`, ограничитель ~1.8 rps, экспоненциальный
backoff с jitter, потолок попыток из `Settings`, ETag), `tvmaze/models.py` (pydantic-модели
только на нужные поля — `image`, `_links`, `externals` отбрасываются на входе, а не на выходе),
`storage/schema.sql` (таблицы и FTS5 из дизайна), `storage/repo.py`, `storage/sync.py`,
`cli.py` с `sync --full` / `sync --updates`.

**Логи.** `page/of/rows/elapsed_s` на обходе; каждый 429 — WARNING с `sleep_s`.

**Тесты.** `integration`: respx-мок отдаёт две страницы → в БД ровно те строки, поля-мусор
отсутствуют. 429 на первой попытке → успех на второй, `sleep` замокан. 429 на всех →
доменная ошибка, а не `httpx.HTTPStatusError` наружу. `unit`: генерация slug, коллизия
`name+year` → суффикс; чистка HTML; усечение `summary`.

**Готово, когда.** `uv run tvtracker sync --full` кладёт ~92 000 сериалов в SQLite,
в логе **ноль** строк уровня ERROR, размер БД < 60 МБ, повторный запуск идемпотентен.

Документация: [TVmaze API](https://www.tvmaze.com/api) — `/shows?page=`, `/updates/shows`,
лимит ~20 запросов / 10 сек на IP, лицензия CC BY-SA.

### Этап 2 — скелет MCP и `show_search` по названию

**Пишем.** `server.py`: `configure_logging()` → `MCPServer("tvtracker", lifespan=...)`.
Lifespan открывает соединение с SQLite и http-клиент, отдаёт `AppContext`
([Lifespan](https://py.sdk.modelcontextprotocol.io/handlers/lifespan/)). `tools/show_search.py`
пока только `by="title"`. `domain/format.py` — строковый рендер результата (concise-строка
из дизайна). Аннотации: `ToolAnnotations(read_only_hint=True, open_world_hint=False)`.

**Тесты.** `contract`: `tools/list` содержит ровно один инструмент с ожидаемой схемой;
`tools/call` возвращает текст, а не JSON API. `unit`: рендер одной строки результата —
6 полей, ни одного лишнего.

**Готово, когда.** В MCP Inspector (`uv run mcp dev src/tvtracker/server.py`) виден
`tools/list`, вызов возвращает компактный текст, в stdout не ушло ни байта постороннего
(проверяется контрактным тестом на `capsys`).

### Этап 3 — поиск по описанию + `catalog://facets`

**Пишем.** `index/fts.py` (BM25 по `summary_clean` + `name` + жанрам, экранирование
пользовательского ввода), `by="auto"` (эвристика «похоже на название» против «похоже на
описание»), ресурс `catalog://facets` с `mime_type="text/plain"`.

**Тесты.** `unit`: эвристика `auto` на 20 размеченных запросах. `integration`: FTS-индекс
на срезе из 200 сериалов — «сотрудникам разделяют память» даёт Severance в топ-3.
`contract`: `resources/read("catalog://facets")` возвращает `text/plain` и укладывается
в ~150 токенов. Безопасность: запрос с кавычкой и `OR foo*` не роняет FTS и не выполняет
оператор.

**Готово, когда.** Сценарий eval №1 проходит и закреплён `regression`-тестом.

### Этап 4 — трекинг, ленивые эпизоды, три ресурса

**Пишем.** `tools/tracking_update.py` (enum-действие, парсер `"2x03"`, ошибка формата с
подсказкой), ленивая загрузка эпизодов через `/shows/:id?embed=episodes` при
`action="track"`, `domain/backlog.py`, ресурсы `tracking://watching`, `tracking://backlog`,
`tracking://schedule`. После изменения — `await ctx.notify_resource_updated(uri)`
([Subscriptions](https://py.sdk.modelcontextprotocol.io/handlers/subscriptions/)).

**Тесты.** `unit` — сердце этапа: все граничные случаи бэклога из списка выше, на чистых
фикстурах, без БД. `contract`: `tracking_update` помечен как изменяющий (не `read_only`);
после вызова клиент получает уведомление об изменении ресурса. Ошибка `"S02E03"` →
`ToolError` с текстом, из которого видно, что подставить.

**Готово, когда.** Сценарий №2 проходит **без единого вызова инструмента** ради истории:
контрактный тест считает вызовы и падает на втором.

### Этап 5 — профиль, поиск серий, `watch_next`, вкус, промпты

**Пишем.** `show_profile` (агрегат четырёх эндпоинтов + рейтинговый профиль по сезонам +
позиция пользователя), `episode_search` с защитой от спойлеров, `watch_next`
(`domain/verdict.py` + ранжирование), `tracking://taste` (`domain/taste.py`), четыре промпта
через `@mcp.prompt()`.

**Тесты.** `unit`: рейтинговый профиль по сезонам на синтетике (сезон проседает — это видно);
`taste` на 34 сериалах даёт ровно те строки, что в дизайне; спойлер-фильтр — серия после
текущей позиции не отдаёт описание **ни при каком** `response_format`. `contract`:
`prompts/get("whats_next", {"minutes": "60"})` рендерится и содержит правила из дизайна.

**Готово, когда.** Сценарии 3–8 проходят, спойлерный сценарий 11 закреплён отдельным тестом.

### Этап 6 — evals, замеры, правка описаний

**Пишем.** `evals/runner.py`: гоняет 12 сценариев, считает **число вызовов** и **токены
ответа** из структурированного лога, кладёт отчёт в `evals/reports/`.

**Готово, когда.** Есть таблица «было/стало» по числу вызовов и токенам; пороги дизайна
выполнены: типовой сценарий 1–2 вызова, concise-ответ до ~600 токенов, сценарий 12
(сериал с 400+ сериями) не более 2 000 токенов на вызов.

### После 6 — опционально

Гибридный поиск (`fastembed` + `sqlite-vec`, слияние с BM25 через RRF) и перевод на
Streamable HTTP. Второе — прямая проверка тезиса о разделении слоёв: доменный слой
и тесты `unit` не должны измениться **ни на строку**.

## Риски и что с ними делать

| Риск | Как проявится | Ответ |
| --- | --- | --- |
| Дизайн писался под SDK v1 | `FastMCP` не импортируется | сверять каждый примитив по docs v2 перед написанием; в коде — только v2-пути (уже проверены импортом) |
| Диск `C:` заполнен (0 ГБ свободно) | падают установки и кэш | кэш `uv` вынесен на `D:` — закрепить переменной `UV_CACHE_DIR` |
| Bootstrap-обход упирается в лимит | 429 в середине обхода | ограничитель 1.8 rps + backoff; повторный запуск идемпотентен и продолжает с места |
| Формат ответов «уплывает» между этапами | молча ломается eval | золотые файлы: любое изменение вывода — видимый diff |
| Непрямая инъекция через `summary` | текст пользователей TVmaze в контексте | чистка HTML, усечение, маркер источника; ограничение записано в README честно |
| Дрейф покрытия домейна | логика уезжает в слой MCP | порог 90 % на `domain/` в CI |
